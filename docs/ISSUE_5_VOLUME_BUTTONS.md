# Issue #5 — hardware Save Moment input

On iOS 17.2 or newer the camera screen hosts Apple's public `AVCaptureEventInteraction` from AVKit. iOS 17.0–17.1 retain the onscreen Save Moment control and the deployment target remains 17.0. The interaction is enabled only for a real, running capture session while the foreground camera screen's central `model.canSave` guard is true. The release callback checks those conditions again and calls `model.save()`; hardware events never start or resume capture.

The router arms an eligible `.began` and saves once on `.ended`. Repeated begin/end callbacks, a cancelled press, state changes during a held press, and old callbacks retained across disable/re-enable or dismantling cannot bypass the guard. SwiftUI updates replace the guard/save closures without dropping an eligible press. Disabling removes the interaction; re-enabling creates a fresh interaction with an activation token. The transparent UIView overrides hit testing to return false while retaining interaction delivery, allowing onscreen controls and dim-screen wake gestures to receive touches.

`CapturePressRouterTests` cover rapid presses, long holds, cancellation, duplicate/reentrant releases, callback replacement, fresh readiness checks, stale activation callbacks, all availability gates, transparent hit testing, and interaction removal. `HardwareSaveRoutingTests` exercise the real model save path with controlled camera/saver dependencies: active-ready saves once, and stopped, starting, empty, saving, hidden, background, stop-during-press, and interrupted states reject callbacks. Tests inject running-session eligibility; they do not simulate physical hardware success. Existing simulator UI save/navigation tests remain the onscreen regression check.

Physical iPhone verification is **pending**. On a supported real iPhone, check both volume buttons separately: one clip for each complete press, one clip for a held press, rapid presses while saving, and saving while dimmed. Begin a press and then stop capture, open the library/playback, background the app, or trigger a camera/audio interruption; releasing must not save or restart capture. Verify normal volume behavior outside active eligible capture, including before Start, during empty/startup/saving states, library/playback, and after leaving the camera. Confirm onscreen controls and dim wake touches remain usable. On iOS 17.0–17.1 verify the onscreen fallback. No physical-button, device-volume, minimum-OS runtime, or dim-hardware result is claimed by simulator/unit tests.

No system-volume observation/change, private API, hidden MPVolumeView, background capture, or microphone behavior is added. References: [Apple capture event interaction](https://developer.apple.com/documentation/avkit/avcaptureeventinteraction), [Apple event phases](https://developer.apple.com/documentation/avkit/avcaptureeventphase/cancelled), and [app1 public capture interaction](https://github.com/esdu/app1/blob/0cb27b3f8ca5f4e4e1cccc65ec96d20c548ee7a1/RewindCam/Views/PreviewViews.swift#L51-L79).
