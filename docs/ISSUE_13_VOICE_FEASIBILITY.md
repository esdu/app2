# Issue #13 — optional on-device voice save assessment

**Decision: defer production implementation; permit a separately reviewed, opt-in prototype after the recorder, preferences, and feedback foundations land.** This assessment completes the bounded scope of [app2 #13](https://github.com/esdu/app2/issues/13). It does not enable voice, add permissions, start recognition, or establish hardware support. Public hardware-button capture (#5) is the lower-complexity first option; voice may still help users who cannot reach a button.

Reviewed 2026-11-16 against app2 `a9a396118bb1dba673238a90772397ad955beb0d` and the pinned app1 reference `0cb27b3f8ca5f4e4e1cccc65ec96d20c548ee7a1`. No physical iPhone, speech prototype, recognition session, battery measurement, or Xcode execution was available for this assessment. All device/OS/locale support and recognition/energy results remain **unvalidated**.

## Evidence and integration boundary

- App2's [camera service](https://github.com/esdu/app2/blob/a9a396118bb1dba673238a90772397ad955beb0d/LittleMoments/Camera/CameraService.swift) exposes start/stop/snapshot/release, with no speech sink. Its [capture engine](https://github.com/esdu/app2/blob/a9a396118bb1dba673238a90772397ad955beb0d/LittleMoments/Camera/CaptureEngine.swift) adds microphone input/output only when clip audio is enabled, then appends audio to the segment writer. Voice therefore needs a separate microphone intent and a bounded tap on that existing audio output; simply attaching a recognizer would fail for silent clips.
- App2's [permission flow](https://github.com/esdu/app2/blob/a9a396118bb1dba673238a90772397ad955beb0d/LittleMoments/Camera/Permissions.swift) requests camera/microphone on explicit capture start, and [Info.plist](https://github.com/esdu/app2/blob/a9a396118bb1dba673238a90772397ad955beb0d/LittleMoments/Resources/Info.plist) has no speech key. The [model](https://github.com/esdu/app2/blob/a9a396118bb1dba673238a90772397ad955beb0d/LittleMoments/App/CameraModel.swift) launches stopped, invalidates asynchronous starts with an operation token, stops in the background, and serializes saves. It does not yet expose the complete central readiness gate required below; reuse #4's implementation when integrated rather than duplicating a weaker voice guard.
- App1 demonstrates [existing-audio fan-out and on-device requests](https://github.com/esdu/app1/blob/0cb27b3f8ca5f4e4e1cccc65ec96d20c548ee7a1/RewindCam/Engine/VoiceTrigger.swift), [separate clip/microphone intents and authorization session token](https://github.com/esdu/app1/blob/0cb27b3f8ca5f4e4e1cccc65ec96d20c548ee7a1/RewindCam/Model/AppModel.swift#L349-L383). Its task callbacks lack task identity: after A is canceled and B starts, A can restart/cancel B. [App1 #2](https://github.com/esdu/app1/issues/2) reports this from code inspection, without device confirmation. Independently avoid the defect; copying this class or waiting for that issue is unnecessary.
- The current project targets iOS 17.0. Apple's `supportsOnDeviceRecognition` and `requiresOnDeviceRecognition` APIs are available from iOS 13, but API availability establishes no particular device/locale capability. Current Speech documentation also describes SpeechAnalyzer; adopting a newer API or raising the deployment target is outside this assessment. ([Capability API](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition), [request requirement](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition), [Speech framework](https://developer.apple.com/documentation/speech))

## Capability and permission matrix

This is an eligibility policy, not a tested support list. At explicit opt-in/start, query the actual selected locale, recognizer, authorization, and current availability. Record device model, exact OS build, locale, and results in prototype evidence; **no supported combination has yet been established**. Do not silently substitute a different language. `supportedLocales()` alone is insufficient because some locales require a network; compare the recognizer's actual locale and require both `supportsOnDeviceRecognition == true` and `isAvailable == true`. Set `requiresOnDeviceRecognition = true` on **every** request before task creation; if capability is false/unknown or either check fails, create no task. No retry may relax this constraint. ([Apple locale availability](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportedlocales()), [on-device support](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition), [required request setting](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition))

| Condition / intent | Microphone and speech behavior | Capture / save behavior |
| --- | --- | --- |
| Voice off; clip audio off | No microphone or speech request/task | Silent capture and onscreen save work |
| Voice off; clip audio on | Existing microphone permission; no speech request/task | Existing sound recording behavior |
| Voice opt-in selected while stopped; permissions undetermined | Explain listening first; request microphone and speech only for immediate use; wait without arming capture | No automatic capture; require explicit Start after a prompt/lifecycle suspension |
| Speech denied/restricted or still undetermined | Voice unavailable; no repeated prompts or task; offer Settings guidance where appropriate | Onscreen save and ordinary capture remain available under their own permissions |
| Microphone denied; clip audio off | Voice unavailable; never start another audio session | Silent capture remains available |
| Microphone denied; clip audio on | Voice unavailable; existing audio permission error, with explicit option to turn clip audio off | Do not silently change the user's clip-audio intent |
| Authorized mic + speech; matching locale; on-device supported and available | Eligible only with explicit voice opt-in and foreground, visible, actively buffering camera | Trigger uses shared readiness/save path |
| Missing recognizer, wrong locale, on-device unsupported/unknown, or unavailable | No task, no server fallback; voice-only status explains unavailable | Ordinary capture/save continue |
| Permission revoked, route interrupted, background, lock, library navigation, capture stop/failure | Detach tap, invalidate tokens, end audio/cancel task and timers; listening off | Preserve foreground-only capture policy and committed clips; explicit restart required |

Speech authorization is separate from microphone authorization. Apple requires `NSSpeechRecognitionUsageDescription` for `SFSpeechRecognizer`, including on-device requests; absence can crash authorization. Authorization callbacks are asynchronous and are not guaranteed on the main queue. Prompt only at feature use, never on app launch or ordinary non-voice capture. ([Apple permission guidance](https://developer.apple.com/documentation/speech/asking-permission-to-use-speech-recognition), [authorization callback](https://developer.apple.com/documentation/speech/sfspeechrecognizer/requestAuthorization(_:)))

## Proposed audio and save boundary

Use one `AVCaptureSession` and its existing `AVCaptureAudioDataOutput`. Compute `needsMicrophone = includeClipAudio || voiceOptInAndEligible`; keep `includeClipAudio` as the independent writer configuration so muted clips never acquire an audio track. Require stopped configuration changes followed by explicit Start rather than silently rebuilding live capture to add a microphone. Feed the writer first and an optional bounded recognition adapter second; never introduce AVAudioEngine, a second capture session, or competing audio-session activation. Apple accepts existing `CMSampleBuffer` input through `appendAudioSampleBuffer`, so another microphone capture pipeline is unnecessary. ([Apple buffer request](https://developer.apple.com/documentation/speech/sfspeechaudiobufferrecognitionrequest))

Speech must not block the recorder's sample queue. The prototype must use one serial recognition executor with at most 250 ms of retained pending audio (also cap buffer count/bytes from the actual format). On overflow, clear/detach and report voice unavailable; do not grow a backlog, stall the writer, or fail ordinary capture. This is a proposed bound to validate, not a measured safe operating point. If microphone setup fails solely for recognition with clip audio off, disable voice and retain silent video capture; if clip audio was requested, surface the existing audio error and let the user explicitly choose silent capture. No transcript/audio persistence, analytics content, temporary speech files, or network fallback. Clear transient buffers/transcripts on teardown. Keep app2's storage caps, protected clips, snapshot leases, and atomic publication unchanged.

Every voice event carries its capture-session and recognition-task identities to the main actor. Immediately before dispatch, recheck current identities, opt-in/listening, cooldown, and **the same `canSave` guard as onscreen/hardware input**: foreground, camera screen visible, buffering, positive buffered duration, no transition, no save in progress. Then call the model's normal save entry point; never snapshot/export directly from speech. A button/voice race must produce one save. Confirmation means the protected local clip was committed, using #4 feedback; recognizing a phrase alone is not a successful save. Save failures use the existing actionable error path.

## Lifecycle and stale-callback isolation

Maintain a capture/session generation **S**, authorization generation **A**, and per-task generation **T** on one serial state owner. Each callback, timer, queued audio item, and main-actor save event captures the relevant identities. Invalidation happens **before** external `endAudio()`/`cancel()` calls. A callback for any obsolete identity is a no-op: it cannot mutate status, clear B, schedule retries, consume cooldown, or save. App1's model-level authorization token alone does not protect individual recognition tasks.

| State / event | Action | Next state |
| --- | --- | --- |
| Off / explicit enable | Explain mic use; reserve S/A before authorization | Authorizing |
| Authorizing / result | Revalidate S/A, opt-in, foreground and explicit capture intent; denied/restricted disables voice | Ready, or Unavailable; prompts that suspended capture require Start |
| Ready / explicit Start and all gates valid | Reserve T and install pending request identity before invoking task factory; set on-device requirement; attach bounded tap | Listening |
| Listening / accepted phrase | Mark this T consumed once; advance T, detach old request, record monotonic cooldown before dispatch; call shared guarded save | Cooldown |
| Listening / normal final result or 50 s timer | Advance T before cancel; schedule at most one eligible replacement, never recursively restart in a callback | Recycling → Listening |
| Listening / transient failure | Advance T, detach/cancel; preserve recorder; recheck capability before bounded retry | Backoff, then Listening or Unavailable |
| Any / stop, opt-out, background, capture interruption, screen exit | Advance S/A/T; remove tap, cancel timers/retries/tasks, clear queues; ignore late callbacks | Off; foreground return never starts capture/listening |
| Any / obsolete callback or timer | No side effects | Unchanged |

Handle synchronous or early fake callbacks during task creation as well as delayed callbacks: reserve the pending T first, route callbacks onto the state owner, and publish the returned task only if S/T are still current. Otherwise cancel that returned task without storing it. Never call recognizer/cancel/user callbacks while holding a lock. `endAudio()` is required when finishing buffer input; cancellation can still produce callbacks, so teardown cannot rely on silence afterward. ([Apple buffer lifecycle](https://developer.apple.com/documentation/speech/sfspeechaudiobufferrecognitionrequest))

Initial prototype policy: exact normalized token-boundary match for one explicitly displayed locale-specific phrase; one accepted phrase per T; 3 s monotonic cooldown retained across task recycling. Repeated partial/final transcripts from that task cannot retrigger. During saving/cooldown do not queue a later save. A fresh request after cooldown avoids replay of the prior cumulative transcript; phrase loss during that gap is a measured false-negative case. Do not treat contextual hints as a reliable command recognizer or promise speaker identification.

Use a monotonic 50 s maximum task timer independent of incoming samples, one active request, and one pending restart timer. Apple's recognizer guidance advises planning for a one-minute task limit; 50 s is a conservative prototype choice, not proof of stable all-day recognition. Limit failure retries to two per explicit listening session, after 1 s then 4 s, with at least 1 s between any task creations; exhausted budget disables voice until explicit re-enable. Three unconsumed tasks ending within 2 s each in a 10 s window also disable voice, preventing a normal-final restart loop. Successful/normal recycling must not replenish the failure budget, and cancellation callbacks never count as failures/restarts. These values need hardware tuning, especially phrase-boundary gaps and resource growth. ([Apple recognition limits](https://developer.apple.com/documentation/speech/sfspeechrecognizer))

## Privacy and accessible product language

Default voice **off**. A future #3 preference may store opt-in and selected validated locale, never recording/listening state; relaunch remains stopped and creates no task or prompt. Show a persistent, VoiceOver-readable listening indicator distinct from clip audio, and announce voice unavailable once without interrupting normal saves. Avoid repeated transcript announcements. Provide onscreen Save, Stop Listening, and accessible status/haptic confirmation; haptics are optional, never the only feedback.

Proposed disclosure: **“Voice Save listens through the microphone while the camera is buffering on this screen. Say ‘save that’ to save a clip. Recognition stays on this iPhone; if on-device recognition is unavailable, Voice Save stops. No speech transcript is stored. It may miss words or save unintentionally.”** When clip audio is off, show **“Clips are silent. The microphone is still listening for Voice Save.”** Turning clip audio off must not imply turning the microphone off while voice remains enabled. Stop/background/lock means listening stops; returning requires explicit capture start.

Only in a future implementation: add `NSSpeechRecognitionUsageDescription` (for example, “Recognize ‘save that’ on this iPhone while Voice Save is enabled to save a moment.”), revise `NSMicrophoneUsageDescription` to describe both independent uses, localize disclosures/phrases, and review privacy policy/App Store disclosures and any newly used required-reason APIs. Do not invent a Speech required-reason manifest category or claim that adding a usage string completes privacy review. Preserve and run source, built-app, and unsigned-archive privacy validation. This documentation-only assessment changes no plist or manifest.

## Hardware-button comparison

| Choice | Benefit | Cost / limitation |
| --- | --- | --- |
| Public capture-event button API (#5) | Explicit physical action, no speech authorization, transcript handling, phrase errors, or recognition worker | User must reach a button; supported hardware/OS event delivery still needs physical validation |
| Optional voice | Hands-free potential when phone cannot be reached | Mic even for silent clips, additional authorization, incidental conversation/media triggers, locale/device availability, task churn and unmeasured energy |

Apple's `AVCaptureEventInteraction` is available from iOS 17.2 and delivers events only during active camera use; disable it when capture cannot handle events to restore normal button behavior. Retain the app's iOS 17.0 fallback and onscreen Save. Prioritize this path; do not claim measured battery savings or complete accessibility equivalence. ([Apple capture-event API](https://developer.apple.com/documentation/avkit/avcaptureeventinteraction))

## Acceptance and evaluation plan

Tests below are specifications for a future isolated prototype, **not results**. Fake recognizer tests prove state handling, not speech accuracy, offline support, battery behavior, or device compatibility.

| Layer / case | Required observable outcome |
| --- | --- |
| Fake: A canceled after B begins, late A partial/final/error, old timer | B unchanged; no save, restart, status mutation, or task storm from A |
| Fake: stop/opt-out/background during authorization and task creation; synchronous callback before factory returns | No late tap/task installation, no save; late returned task canceled; foreground return stays stopped |
| Fake: repeated partial/final phrase, final+error in one callback, simultaneous hardware/onscreen event | At most one accepted phrase per T, one guarded save, cooldown preserved across replacements |
| Fake: paused, hidden library, zero buffer, transitioning, saving, stale session event queued to main actor | Zero new saves; no delayed replay when readiness returns |
| Fake: denied/restricted mic or speech; unavailable/wrong locale; support false; capability changes on retry | Voice disabled; zero server-capable requests; silent capture/onscreen save remain usable |
| Fake clock: repeated failures/finals, silence, recycling, clock change | Fixed retry budget and timer/rate bounds; sample-independent recycling; no wall-clock cooldown bypass |
| Production harness (#2): bounded fan-out pressure, tap detachment, recognition failures | Recorder timestamp continuity, bounded memory/storage, A/V correctness, committed-file/lease behavior unchanged; speech failure never propagates as capture failure |
| UI (#3/#4): clean launch and restored opt-in, silent clips with voice, denial, stop, save error/success | No launch prompt/task/capture; honest mic indicator; accessible nonmodal status; confirmation only after commit; playable silent clips truly lack audio |
| Physical: supported candidate tuples, airplane mode/no network, permission revocation, calls/routes, lock/background | Record actual capability and availability values; no server fallback; explicit restart; no hidden listening; ordinary capture survives voice-only failures |
| Physical: repeated recycling, multi-hour run, thermal/battery comparison | Record task counts/restarts/errors, gaps, retained buffers/RSS trend, output correctness and matched energy/thermal observations; no support claim without data |

Build a consented evaluation corpus separately from production logging. Start with en-US as a **candidate**, not supported status: at least 100 intended commands across speakers/accents, distances, orientations and quiet/noisy conditions; at least 4 hours of non-command conversation, TV/music, near-matches, quoted commands and silence. Test around recycling/cooldown boundaries and during saves. Count unintended saves per listening hour, missed eligible intended commands/total, duplicates per utterance, and end-of-phrase-to-committed-clip latency (p50/p95). Report confidence intervals and raw denominators; count quoted/media phrases as unintended triggers when the user did not intend a command. Add locales only after an equivalent corpus and actual capability checks. Set product acceptance thresholds before collecting acceptance data; the assessment supplies no invented accuracy target or successful result.

For energy/thermal comparisons, use matched runs on the same recorded device/OS/build, locale, battery start range, charger state, brightness/dim mode, 720p/fps/clip-audio setting, scene, temperature, duration and save schedule: voice off, voice on, then hardware-button baseline, repeated with order varied. Include silent clips + voice as a separate condition. Record battery delta alongside available power/thermal instrumentation and measurement uncertainty; compare memory/task growth and A/V continuity over at least a two-hour session. Stop unsafe thermal runs normally. Actual duration, conditions and all results are currently unknown; simulator/fake success cannot fill these cells.

## Bounded follow-up and release gate

After #2, #3 and #4 land, propose a separate opt-in prototype branch with an injected recognizer/clock, one generation-scoped adapter and audio tap, independent clip-audio intent, and the tests above. Keep production voice absent until the capability ledger, privacy/UI review, state tests and physical evaluation justify a separate shipping decision. Do not add background modes, server recognition, a second microphone owner, automatic recording restoration, raised storage caps, or continuous transcript storage. Coordinate with #5's shared trigger gate and #7's capture-stop behavior; neither substitutes for voice lifecycle tests.

Remain deferred if no hardware is available, on-device recognition cannot be enforced, task/resource behavior is unbounded, speech failures affect capture, or false triggers/misses/energy cost fail the predeclared product limits. A completed assessment is a documented decision, not implementation completion or permission to enable the feature.
